# เลือกโฮสต์ Watermelon AI ฟรีอย่างตรงไปตรงมา

**คำแนะนำหลัก ณ 13 ตุลาคม 2026 คือ ทดลองใช้ Oracle Cloud Infrastructure (OCI) Always Free A1 VM หนึ่งเครื่องเป็นทางเลือกแรก หากเป้าหมายเคร่งครัดคือไม่เสียค่าโฮสต์รายเดือนและต้องการให้ Node API, FastAPI vision และ Ollama รันค้างอยู่ร่วมกัน** เพราะเป็นทางเลือกที่เข้ากับฐานข้อมูล JSON, โฟลเดอร์อัปโหลด, one-writer lock และการเรียก Ollama ผ่าน loopback ของโค้ดปัจจุบันมากที่สุด โดยแทบไม่ต้องแก้แอป อย่างไรก็ดี คำว่า “ตลอด” ในที่นี้หมายถึง VM ที่ตั้งใจให้รันต่อเนื่อง ไม่ใช่การรับประกัน: Oracle อาจเรียกคืนเครื่องฟรีที่เข้าเกณฑ์ idle, อาจไม่มี A1 capacity และ Free Tier ไม่มี SLA หรือสิทธิ์ซัพพอร์ต ([OCI Always Free](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm); [Oracle Free Tier FAQ](https://www.oracle.com/cloud/free/faq/)). หากให้ความสำคัญกับความน่าเชื่อถือในการดูแลระบบและผู้ใช้ในไทยมากกว่าการไม่มี cold start ให้ใช้ Firebase Hosting + Node Cloud Run + FastAPI Cloud Run ในสิงคโปร์เป็นเป้าหมายระยะถัดไป แต่กำหนด `min-instances=0`: URL จะเรียกได้ตลอดและระบบตื่นเมื่อมีคำขอ ทว่าโปรเซสไม่ได้ warm ตลอด และมีโอกาสเกิดค่าใช้จ่ายเกินโควตา ([Cloud Run autoscaling](https://docs.cloud.google.com/run/docs/about-instance-autoscaling); [Cloud Run pricing](https://cloud.google.com/run/pricing)). **ไม่มีผู้ให้บริการที่ตรวจสอบแล้วรายใดรับประกัน production-grade, always-warm และ free forever พร้อมกัน**

## “เปิดได้ตลอด” มีสองความหมายที่ให้ผลต่างกัน

**Always-warm** หมายถึงโปรเซสและโมเดลอยู่ในหน่วยความจำตลอด พร้อมตอบคำขอแรกทันที; OCI VM เข้าใกล้เงื่อนไขนี้ที่สุดในกลุ่มฟรี แต่ยังเป็น best-effort และผู้ดูแลต้องรับผิดชอบแพตช์ ระบบเครือข่าย TLS การเฝ้าระวัง และการกู้คืนเอง ส่วน **always-reachable แบบ scale-to-zero** หมายถึง URL ยังคงอยู่ แต่แพลตฟอร์มเริ่ม container ใหม่เมื่อมีคำขอแรก Cloud Run ใช้รูปแบบนี้เมื่อ `min instances = 0`; การกำหนด warm minimum มีค่าใช้จ่าย และ instance ยังสามารถ restart ได้ ([Cloud Run minimum instances](https://docs.cloud.google.com/run/docs/configuring/min-instances)). สำหรับงานวินิจฉัยภาพ cold start ยังรวมเวลาเริ่ม Python และโหลด ONNX ทุกโมเดล จึงต้องวัดด้วย image จริง ไม่ใช่อาศัยเวลา cold start ของตัวอย่าง hello-world

| ทางเลือก | สถานะเมื่อไม่มีทราฟฟิก | ความเข้ากันกับ repo ปัจจุบัน | ข้อจำกัดชี้ขาด | คำตัดสิน |
|---|---|---|---|---|
| OCI Always Free A1 VM | รันค้างได้ แต่มี idle reclamation | สูง: มี persistent block disk และวาง 3 โปรเซสในเครื่องเดียวได้ | ARM64 ต้องทดสอบ, capacity ไม่แน่นอน, ไม่มี SLA | **เริ่มจากตัวนี้เมื่อห้ามมีค่าโฮสต์** |
| Cloud Run (Singapore) | scale-to-zero; URL ตื่นตามคำขอ | กลาง: รองรับ container แต่ disk ไม่ถาวร | ต้องย้าย state/uploads, ผูก billing, cold start และอาจมีค่า egress/overage | **เป้าหมาย managed ที่เหมาะกับผู้ใช้ไทย** |
| Modal Starter | scale-to-zero | เหมาะกับ vision แบบงานเป็นคิว มากกว่าระบบทั้งก้อน | เครดิต compute $30/เดือน ไม่ใช่ unlimited และเกินแล้วคิดเงิน ([Modal pricing](https://modal.com/pricing)) | ทางสำรองสำหรับ vision ที่ทราฟฟิกไม่สม่ำเสมอ |
| Render / Koyeb Free | sleep เมื่อ idle | ต่ำสำหรับ vision และ local state | 0.1 CPU/512 MB, disk ไม่ถาวร; Render ตื่นราวหนึ่งนาที ([Render Free](https://render.com/docs/free); [Koyeb instances](https://www.koyeb.com/docs/reference/instances)) | ใช้เดโมสั้น ๆ เท่านั้น |
| Vercel / Cloudflare Workers | serverless/isolate | ต่ำโดยไม่ออกแบบใหม่ | Vercel จำกัด payload ฟังก์ชัน 4.5 MB; Workers Free มี CPU 10 ms และ filesystem ชั่วคราว ([Vercel limits](https://vercel.com/docs/functions/limitations); [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)) | ไม่เหมาะกับ API+vision รูปแบบปัจจุบัน |

## โครงสร้างจริงทำให้ VM ได้เปรียบในระยะสั้น

Watermelon AI ไม่ใช่เว็บ API ตัวเดียว แต่เป็น **Express/Node gateway, FastAPI/ONNX vision และ Ollama** เมื่อเปิดความสามารถครบ เบราว์เซอร์ควรเรียกเฉพาะ Node; Node เรียก vision ผ่าน `VISION_SERVICE_URL` ขณะที่ Ollama ถูกผูกกับ `127.0.0.1:11434` ใน `server-chat-provider.ts` ดังนั้นการวางทั้งสามโปรเซสบน VM เดียวและ bind FastAPI/Ollama ไว้เฉพาะ loopback ตรงกับ trust boundary ปัจจุบันที่สุด Root Docker image ไม่บรรจุ Ollama หรือ `.local-ai`; หากแยกไป Cloud Run แชตด้วยโมเดลจะทำงานได้ก็ต่อเมื่อเปิด Gemini แบบมีค่าใช้จ่ายอย่างชัดเจน มิฉะนั้นเส้นทางนั้นจะตอบ 503 ตามนโยบายปัจจุบัน

**อุปสรรคใหญ่ที่สุดคือความถูกต้องของข้อมูล ไม่ใช่จำนวน 36 endpoints** `server-storage.ts` ยังเก็บข้อมูลหลัก, audit log และ uploads บน local disk และป้องกัน writer ตัวที่สองเพื่อไม่ให้ข้อมูลทับกัน ขณะที่ Cloud Run ระบุว่า filesystem ใน container อยู่ในหน่วยความจำและหายเมื่อ instance หยุด ([Cloud Run container contract](https://docs.cloud.google.com/run/docs/container-contract)). Firestore ที่มีอยู่ใน repo ทำให้ถาวรเฉพาะ conversation/message ยังไม่ครอบคลุม user, consent, plot, report, disease record, audit และไฟล์อัปโหลดทั้งหมด การเปิด autoscaling ก่อนย้าย state จึงเสี่ยงทั้งข้อมูลหายและ concurrent write ผิดพลาด แม้ Firestore มี free quota แต่โควตามีขอบเขต และเมื่อเปิด billing แล้ว budget alert ไม่ใช่ hard cap ([Firestore pricing](https://cloud.google.com/firestore/pricing)).

FastAPI ปัจจุบันโหลด ONNX หลาย session ตอนเริ่มโปรเซสและใช้หนึ่ง Uvicorn worker; ชุดไฟล์ vision ใน repo มากกว่า 100 MiB และต้องวัด peak RAM/CPU จริงก่อนกำหนดเครื่อง 512 MiB หรือ concurrency สูง นอกจากนี้ Node รับ JSON ได้ถึง 50 MiB, upload ที่ถอดรหัสแล้วถึง 12 MiB และ vision ถึง 10 MiB จึงชนข้อจำกัด payload ของ Vercel โดยตรง ([Vercel Function limits](https://vercel.com/docs/functions/limitations)). ระบบไม่ต้องการ WebSocket แต่มี timeout งาน 60–180 วินาที จึงต้องตรวจ proxy timeout และทดสอบ request ใหญ่บนเครือข่ายมือถือไทย

## แผนลงมือทำเริ่มฟรีก่อนแล้วค่อยย้าย managed

| ระยะ | งานที่ต้องทำ | เกณฑ์ผ่านก่อนเดินต่อ |
|---|---|---|
| 1. พิสูจน์ OCI | ตรวจ allowance จริงใน Console และหา A1 capacity; สร้าง Ubuntu ARM VM กับ block volume; ทดสอบ Node 24, `onnxruntime`, Pillow, NumPy, Ollama/Qwen และ inference แบบ `legacy4`/`wide9` | build/test ผ่านบน ARM64, โหลดทุก model ได้, วัด peak RSS และเวลา inference จริง |
| 2. เปิดบริการแบบ single-host | build `dist`; รัน Node ที่พอร์ต 3000, FastAPI ที่ `127.0.0.1:8000`, Ollama ที่ `127.0.0.1:11434`; เปิดสู่ภายนอกเฉพาะ Node ผ่าน Caddy/Nginx พร้อม HTTPS | หน้าเว็บ, auth/OTP, upload ใหญ่, diagnosis และ chat ผ่าน end-to-end โดย FastAPI/Ollama เข้าจากอินเทอร์เน็ตไม่ได้ |
| 3. ทำให้ดูแลได้ | ใช้ `systemd` ให้สามโปรเซสกลับมาหลัง reboot; ตั้ง firewall, log rotation, health check, monitoring; สำรองแบบเข้ารหัสสำหรับ `data/`, `uploads/` และ `.local-ai/models` แล้วทดสอบ restore | reboot แล้วระบบฟื้นเอง, restore ได้จริง, error ไม่ถูกกลืนเป็นค่า default |
| 4. เตรียมทางย้าย | วัด cold start, p95 latency, RAM, CPU, ปริมาณภาพ และ egress จากผู้ใช้ไทย พร้อมกำหนดงบสูงสุดที่ยอมรับได้ | รู้ว่าผู้ใช้รับ first-scan delay ได้เท่าไรและ free quota เพียงพอหรือไม่ |
| 5. ย้ายสู่ managed เมื่อจำเป็น | ย้าย `watermelon_db.json`/audit ทุก collection ไปฐานข้อมูล transactional และ uploads ไป object storage; เพิ่ม authenticated Node→private vision call; ใส่ Firebase `/api/**` rewrite ก่อน SPA catch-all; จากนั้น deploy Node/vision แยก Cloud Run ที่ `min=0`, จำกัด max instances และตั้ง budget alerts | ปิด local-state fallback ใน production, vision ไม่เปิด public, ทดสอบ rollback/restore และ failure/cold-start UX ครบ |

ระยะ 1–3 **ไม่ต้องเปลี่ยน source code** หากรันสามโปรเซสบน host network เดียวตาม loopback ที่มีอยู่ แต่ต้องตั้ง production environment ให้ถูกต้อง ได้แก่ `NODE_ENV=production`, secret ใหม่สำหรับ JWT/storage, ปิด demo OTP, กำหนด `TRUST_PROXY`/`ALLOWED_ORIGINS` และห้ามเปิด FastAPI/Ollama สู่สาธารณะ หากใช้ container แยก network namespace จะชน URL Ollama ที่ hard-code อยู่และต้องผ่านการตัดสินใจของเจ้าของ backend ก่อน ส่วนระยะ 5 เป็นงานแก้ backend จริง และ `package.json`/deployment config ต้องประสาน Antigravity ตามข้อตกลงใน `AGENTS.md`

## ความน่าเชื่อถือขึ้นกับข้อมูลถาวรและการล้มอย่างโปร่งใส

สำหรับผู้ใช้เกษตรกร ความน่าเชื่อถือไม่ได้เท่ากับแค่ URL ตอบ 200 แต่หมายถึงบันทึกไม่หาย ผลวินิจฉัยไม่ถูกแต่งเมื่อเครื่อง vision ตื่นช้า และฟีเจอร์เสียเงินไม่ถูกเปิดโดยไม่ตั้งใจ ดังนั้นห้ามใช้ keep-alive ping เป็นคำตอบเรื่อง uptime เพราะมันกินโควตาและไม่สร้าง SLA; ห้าม fallback จาก durable storage ไป ephemeral disk ใน production; และห้ามเปลี่ยน engine อัตโนมัติเมื่อ inference ล้มเหลว `legacy4` ต้องยังเป็นเส้นทางวินิจฉัยหลัก ส่วน `wide9`/`claude` ต้องคงสถานะเป็นตัวเลือกเสริมและไม่ยืมตัวเลขความแม่นยำของ `legacy4`

Cloud Run มี free allowance แบบรายเดือน รวม 2 ล้าน requests และโควตา CPU/RAM ตาม request-based billing แต่ต้องผูก Cloud Billing และการใช้เกิน allowance บนบัญชีชำระเงินอาจถูกคิดเงินจริง; Google ระบุว่า Free Tier ไม่มีวันสิ้นสุดที่กำหนดไว้แต่สามารถเปลี่ยนเงื่อนไขโดยแจ้งล่วงหน้าได้ ([Google Cloud Free Program](https://docs.cloud.google.com/free/docs/free-cloud-features)). OCI เองต้องใช้บัตรเพื่อยืนยันตัวตนในกรณีทั่วไป, capacity ฟรีไม่ได้สงวนไว้ และ Free Tier ไม่มี SLA ([Oracle Free Tier](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm); [OCI capacity troubleshooting](https://docs.oracle.com/en-us/iaas/Content/Compute/Tasks/troubleshooting-out-of-host-capacity.htm)). ข้อเท็จจริงสองชุดนี้ทำให้การสื่อสารที่ซื่อตรงที่สุดคือ **“เปิดให้เรียกใช้ได้โดยตั้งเป้าไม่มีค่าบริการ ภายใต้โควตาและข้อจำกัดของผู้ให้บริการ”** ไม่ใช่ “ออนไลน์ 100% ฟรีตลอดกาล”

## Conclusion

Watermelon AI ควรเริ่มด้วย OCI A1 แบบ single-host เพื่อพิสูจน์ระบบจริงโดยไม่ฝืนสถาปัตยกรรมและไม่เสียค่าโฮสต์ประจำ พร้อมเตรียม deployment automation และ backup เพื่อย้ายหนีได้เมื่อ capacity หรือเงื่อนไขเปลี่ยน จุดตัดสินใจย้ายไป Cloud Run ไม่ควรเป็นเพียงจำนวนผู้ใช้ แต่คือวันที่ทีมต้องการ autoscaling, ลดภาระดูแลเครื่อง หรือยอมจ่ายเพื่อ first-request latency ที่สม่ำเสมอ

เส้นทางนี้เปลี่ยนโจทย์จากการตามหา “ฟรีตลอด” ซึ่งไม่มีผู้ให้บริการรับประกัน เป็นการสร้างระบบที่ **เสีย gracefully, รักษาข้อมูล และย้ายแพลตฟอร์มได้**—คุณสมบัติที่สำคัญกว่าคำว่า always-on สำหรับบริการเกษตรที่ผลลัพธ์มีผลต่อการตัดสินใจจริง
