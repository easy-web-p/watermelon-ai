# Watermelon AI repository fit for free hosting

## What processes and services must run, and can Node and FastAPI be separated?

### Takeaway
The application is a three-runtime system when all features are enabled: an Express/Node gateway and web server, a separate FastAPI/ONNX vision service, and Ollama for no-per-call-cost text chat. Node and FastAPI are intentionally separable through `VISION_SERVICE_URL`; the browser should call only Node. Ollama, unlike vision, is hard-coded to loopback and therefore must share Node's network namespace unless that security-sensitive design is deliberately changed.

### Cited Findings
- `npm start` and `npm run dev` both execute `tsx server.ts`; the production Node container uses Node 24, listens on `$PORT` (default 3000 locally, 8080 in its Dockerfile), and serves `dist/` as the SPA after the API routes. Production startup fails if `dist/index.html` is absent. — [package.json](../../package.json#L6-L14); [Dockerfile](../../Dockerfile#L12-L53); [server.ts](../../server.ts#L64-L68); [server.ts](../../server.ts#L2818-L2869)
- The vision service is a distinct FastAPI process. Locally it defaults to `127.0.0.1:8000`; its container listens on `$PORT` at `0.0.0.0` with exactly one Uvicorn worker. Node reaches it by `VISION_SERVICE_URL`, defaulting to `http://127.0.0.1:8000`. — [.env.example](../../.env.example#L99-L110); [fastapi_service/Dockerfile](../../fastapi_service/Dockerfile#L37-L47); [server.ts](../../server.ts#L1701-L1713)
- The frontend API client uses same-origin `/api/v1` by default. A separately hosted frontend or Capacitor build must set `VITE_API_BASE_URL` at build time. In development Vite proxies `/api` to `API_PROXY_TARGET`, default `http://localhost:3000`. — [src/lib/api.ts](../../src/lib/api.ts#L1-L14); [vite.config.ts](../../vite.config.ts#L16-L25); [.env.example](../../.env.example#L37-L46)
- Node is the intended sole caller of FastAPI; FastAPI's source says browsers should reach it through Node. The Python service has CORS but no user authentication. — [fastapi_service/main.py](../../fastapi_service/main.py#L235-L247); [fastapi_service/README.md](../../fastapi_service/README.md)
- The no-per-call-cost chat path is Ollama at a non-configurable `http://127.0.0.1:11434`, model `qwen3.5:4b` by default. If Ollama is unavailable, Node may use Gemini only when both `GEMINI_API_KEY` and explicit `CHAT_ENABLE_GEMINI` opt-in are present; otherwise ordinary model-backed chat returns 503 (some catalogue/safety replies are generated locally without a model). — [server-chat-provider.ts](../../server-chat-provider.ts#L1-L34); [server-cost-policy.ts](../../server-cost-policy.ts); [server.ts](../../server.ts#L913-L958)
- The checked-in Windows helper starts Ollama, stores its model under `.local-ai`, forces local-only mode and one loaded model, downloads the named model if missing, and warms it. It does not start Node or FastAPI. — [scripts/start-local-ai.ps1](../../scripts/start-local-ai.ps1#L1-L62)
- FastAPI can be deployed before Node and passed back as a URL; the repository already contains separate root and `fastapi_service` Dockerfiles. The existing deployment guide explicitly describes Firebase Hosting → Node Cloud Run → vision Cloud Run. — [DEPLOY.md](../../DEPLOY.md#L44-L61); [Dockerfile](../../Dockerfile); [fastapi_service/Dockerfile](../../fastapi_service/Dockerfile)
- The documented Cloud Run vision command marks vision private, but current Node calls it with plain `fetch` and no Google ID token. Google requires a Google-signed OIDC ID token in `Authorization` or `X-Serverless-Authorization` for service-to-service calls to a private Cloud Run service. — [DEPLOY.md](../../DEPLOY.md#L101-L110); [server.ts](../../server.ts#L1757-L1771); [Google Cloud service-to-service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)

### Inferences
- Node and FastAPI should remain separate services on managed hosting: they have different languages, dependencies, memory/concurrency profiles, and Dockerfiles, while the API contract already isolates them.
- A separated, private Cloud Run vision deployment does **not** work as documented today. Either Node must gain an authenticated request helper (preferred), or vision would need to be public. Public vision is contrary to the repository's own safety guidance because anyone could consume CPU or paid Claude calls if enabled.
- Ollama is a third process, not bundled into either Docker image. A cloud deployment using the current root Dockerfile will have text chat only through explicitly enabled Gemini; to retain local Qwen, run all three on one VM/network namespace or deliberately add a configurable, authenticated Ollama endpoint.
- Frontend hosting is independent: it may be Firebase/static hosting with an `/api/**` rewrite, or it may be served directly by Node from `dist/`. The latter is the simplest shape on a single VM.

### Gaps
- The repository does not contain Linux service definitions or a Docker Compose file that starts Node, FastAPI, and Ollama together.
- No measured cold-start, peak RSS, or per-request CPU benchmark is checked in for the complete six-model vision registry; the 2 GiB Cloud Run choice in `DEPLOY.md` is an engineering estimate, not a measured minimum.

## Does the app rely on persistent disk, large models, background processes, WebSockets, or long requests?

### Takeaway
Yes on persistent local disk, CPU/model memory, and potentially long requests; no application WebSocket or SSE endpoint was found. The largest hosting blocker is not the 113 MiB vision bundle but correctness of state: most user/security data and all uploads still live on one local filesystem, with a deliberate one-writer lock.

### Cited Findings
- `server-storage.ts` resolves `data/` and `uploads/` beside the server, creates them at import time, reads/writes `data/watermelon_db.json`, appends security events to `data/audit-log.jsonl`, and writes uploaded bytes to `uploads/`. — [server-storage.ts](../../server-storage.ts#L7-L31); [server-storage.ts](../../server-storage.ts#L136-L217); [server-storage.ts](../../server-storage.ts#L220-L284); [server-storage.ts](../../server-storage.ts#L459-L485)
- Persistence is a whole-object JSON rewrite with a 200 ms debounce and atomic rename where possible. The code refuses a second live writer because two processes would silently overwrite each other's users, plots, consent withdrawals, OTP sessions, and other data. — [server-storage.ts](../../server-storage.ts#L136-L217); [server-storage.ts](../../server-storage.ts#L287-L375)
- Firestore support currently makes only conversations and messages durable/shared. Users, consents, plots, reports, disease records, audit data, and other collections remain in `watermelon_db.json`; uploaded images/audio remain in `uploads/`. The repository's deployment guide explicitly calls both remaining items unfinished. — [server-history-store.ts](../../server-history-store.ts); [DEPLOY.md](../../DEPLOY.md#L333-L353)
- When `HISTORY_FIRESTORE=1`, Node hydrates conversation history at startup and opens a Firestore snapshot listener. If Firestore setup fails it deliberately degrades to local-file history and reports the degradation instead of terminating. — [server.ts](../../server.ts#L418-L437); [server.ts](../../server.ts#L2852-L2862); [.env.example](../../.env.example#L176-L198)
- Cloud Run's writable filesystem is in-memory and does not persist when an instance stops; filesystem writes also consume instance memory. This is incompatible with treating `watermelon_db.json` or `uploads/` as durable state. — [Google Cloud container runtime contract](https://docs.cloud.google.com/run/docs/container-contract)
- Render's free web services similarly have ephemeral filesystems, lose changes on restart/redeploy/spin-down, cannot attach persistent disks, and spin down after 15 idle minutes. — [Render free services](https://render.com/docs/free)
- FastAPI's serving requirements intentionally omit PyTorch and use ONNX Runtime, Pillow, NumPy, FastAPI, Uvicorn, multipart, and Pydantic. The vision Docker image is Python 3.12 slim plus `libgomp1`, JPEG, and zlib runtime libraries. — [fastapi_service/requirements.txt](../../fastapi_service/requirements.txt); [fastapi_service/Dockerfile](../../fastapi_service/Dockerfile#L1-L25)
- Six ONNX files are currently present and copied by the vision Dockerfile. Their local total is 101,845,972 bytes (97.13 MiB); all top-level files in `fastapi_service` total 118,530,369 bytes (113.04 MiB). The registry opens sessions for the three-file wide9 ensemble plus legacy4, wide11, and baseline9 when their files exist, so current runtime behavior is broader than the older “two models / ~34 MB” comment in `DEPLOY.md`. — [fastapi_service/Dockerfile](../../fastapi_service/Dockerfile#L26-L31); [fastapi_service/engines.py](../../fastapi_service/engines.py#L831-L923); [DEPLOY.md](../../DEPLOY.md#L128-L136)
- The legacy ONNX session and all available optional engines load during FastAPI lifespan startup; the container intentionally runs one worker because each worker would load its own model copies. — [fastapi_service/main.py](../../fastapi_service/main.py#L170-L232); [fastapi_service/Dockerfile](../../fastapi_service/Dockerfile#L43-L47)
- Express accepts JSON bodies up to 50 MiB. User file uploads are base64-in-JSON and capped at 12 MiB decoded; FastAPI caps images at 10 MiB. This rules out platforms with small function payload limits without redesigning uploads. — [server.ts](../../server.ts#L64-L68); [server.ts](../../server.ts#L1024-L1050); [fastapi_service/main.py](../../fastapi_service/main.py#L70-L73); [fastapi_service/main.py](../../fastapi_service/main.py#L361-L415)
- Client timeouts are 120 seconds for chat, 60 seconds for ordinary vision/upload, and 180 seconds for Claude comparison. Node defaults local vision to 20 seconds and Claude vision to 180 seconds. The Cloud Run guide configures 300-second service timeouts. — [src/lib/api.ts](../../src/lib/api.ts#L551-L575); [src/lib/api.ts](../../src/lib/api.ts#L610-L638); [server.ts](../../server.ts#L1712-L1745); [DEPLOY.md](../../DEPLOY.md#L101-L110); [DEPLOY.md](../../DEPLOY.md#L190-L199)
- No `WebSocket`, `EventSource`, `text/event-stream`, `res.write`, or upgrade handler occurs in project source outside dependencies. Chat waits for `generateText` and returns one JSON result. Long-lived behavior is limited to the Firestore listener, debounced local writes, and resident model processes. — [server.ts](../../server.ts#L939-L958); [server-history-store.ts](../../server-history-store.ts)

### Inferences
- A single always-running VM with a real block disk matches the present persistence and one-writer model; horizontally scaled stateless/container instances do not, even if conversation history alone is moved to Firestore.
- Function-as-a-service deployment of `server.ts` (for example, converting it into short-lived serverless handlers) is a poor fit without major backend changes: startup currently acquires a writer lock, owns an in-memory database, opens a snapshot listener, serves large JSON uploads, and can wait minutes on upstream inference.
- Model file size itself is manageable on a VM or container image, but RAM/CPU are the binding resources because multiple ONNX sessions load and inference evaluates many crops. A 512 MiB free container should not be assumed viable.
- The application does not need WebSocket support. Conventional request/response proxying is sufficient, but proxy/provider timeout and body-size limits must be at least the application limits.

### Gaps
- No production load test establishes safe concurrency, p95 latency, or minimum memory. Before choosing less than the repository's proposed 2 GiB/2 vCPU for vision, measure the full registry under `balanced`/`deep` inference.
- It is not clear whether all experimental `wide11` and `baseline9` weights should ship in production. Removing models is a model/data decision owned by the backend side and must preserve the engine registry and safety labels; it should not be done merely to fit a free tier.

## What deployment configurations are realistic, what repository changes do they require, and which best fits?

### Takeaway
There is no SLA-backed, genuinely always-warm, production-safe hosted architecture that is both unlimited and free. The best no-platform-fee fit is one persistent VM (OCI Always Free A1 if capacity/account approval is available) running Node, FastAPI, and Ollama together; the best managed low-traffic demo path is Firebase Hosting + two Cloud Run services with scale-to-zero, but it needs backend fixes before user data is safe. A named Cloudflare Tunnel from the owner's always-on PC is the fewest-code-change option but transfers uptime, electricity, security, and backup responsibility to that PC.

### Cited Findings

#### Shape A — One persistent VM (recommended for the strict “no monthly platform fee” target)

- OCI's current Always Free documentation says a free tenancy can use an Ampere A1 allocation equivalent to 2 OCPUs and 12 GB RAM, with 200 GB total Always Free block volume storage; capacity can be unavailable in a home region. Oracle also states that Free Tier has no SLA/support entitlement. — [OCI Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm); [Oracle Free Tier FAQ](https://www.oracle.com/cloud/free/faq/)
- Exact repository/runtime plan: build `dist` with `npm run build`; run FastAPI on `127.0.0.1:8000`; run Ollama on `127.0.0.1:11434`; run Node with `NODE_ENV=production` on 3000; expose only Node through Nginx/Caddy or a named Cloudflare Tunnel; and keep `data/`, `uploads/`, `.local-ai/models`, and backups on the VM's block disk. The existing loopback defaults and production SPA serving already support this topology. — [package.json](../../package.json#L6-L14); [server-chat-provider.ts](../../server-chat-provider.ts#L1-L9); [.env.example](../../.env.example#L93-L110); [server.ts](../../server.ts#L2818-L2869)
- Required new configuration, not application behavior: Linux `systemd` units (or an equivalent supervisor) for Ollama, Uvicorn, and Node; reverse-proxy/TLS config; production `.env` secrets; firewall rules exposing only 80/443; log rotation; and scheduled encrypted backups. The checked-in helper is Windows-only, so it cannot be reused as the Linux service manager. — [scripts/start-local-ai.ps1](../../scripts/start-local-ai.ps1); [server-jwt.ts](../../server-jwt.ts#L18-L50); [.env.example](../../.env.example#L59-L94)
- Source-code changes: none are required if all three processes run directly on the same host network and Node serves `dist`. If containers are used, current hard-coded Ollama loopback means separate Compose containers will not work without either sharing a network namespace or changing `server-chat-provider.ts` to accept a tightly validated internal URL.

#### Shape B — Firebase Hosting + Node Cloud Run + vision Cloud Run + managed persistence

- Cloud Run can scale to zero and provides a monthly free tier, but keeping minimum instances warm is billable and still best-effort; Cloud Run's public pricing lists finite monthly CPU/RAM/request quotas rather than unlimited free service. — [Cloud Run product/pricing](https://cloud.google.com/run); [Cloud Run minimum instances](https://docs.cloud.google.com/run/docs/configuring/min-instances); [Cloud Run pricing details](https://cloud.google.com/run/pricing)
- The repository already has both Dockerfiles and deploy commands proposing 1 GiB for Node, 2 GiB/2 vCPU/concurrency 4 for vision, 300-second timeouts, and `min-instances=0`. This is a scale-to-zero demo configuration, not always-warm hosting. — [DEPLOY.md](../../DEPLOY.md#L96-L136); [DEPLOY.md](../../DEPLOY.md#L183-L209)
- `firebase.json` currently contains only a catch-all SPA rewrite; therefore `/api/**` resolves to `index.html`, not Node. It must add an `/api/**` Cloud Run rewrite **before** the catch-all. Firebase officially supports Cloud Run rewrites and lists `asia-southeast1` as supported (though `asia-east1` is one of the recommended colocated regions for best performance). — [firebase.json](../../firebase.json#L1-L49); [Firebase Hosting rewrites](https://firebase.google.com/docs/hosting/full-config)
- Private vision requires a backend change: centralize all Node→vision fetches behind a helper that obtains/caches a Google ID token for the vision audience, then grants only Node's service account `roles/run.invoker`. This touches `server.ts` (and likely a new backend helper plus a dependency in jointly owned `package.json`). — [server.ts](../../server.ts#L1116-L1121); [server.ts](../../server.ts#L1763-L1771); [server.ts](../../server.ts#L1896-L1923); [Google Cloud service-to-service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service)
- Durable production use requires moving **all** remaining `DatabaseSchema` collections off `watermelon_db.json` and moving `uploads/` to object storage; enabling `HISTORY_FIRESTORE=1` alone is insufficient. Firestore's free quota is finite (1 GiB stored data, 50,000 reads/day, 20,000 writes/day, 20,000 deletes/day, 10 GiB monthly egress for one free database), and requests continue beyond budgets when billing is enabled, so alerts are not a hard spending cap. — [server-storage.ts](../../server-storage.ts#L47-L134); [DEPLOY.md](../../DEPLOY.md#L340-L353); [Firestore pricing and free quota](https://cloud.google.com/firestore/pricing)
- Text chat on this shape needs explicit paid Gemini opt-in because root `Dockerfile` excludes `.local-ai`/Ollama. Otherwise model-backed text chat returns 503; vision remains local ONNX and need not enable paid Claude. — [Dockerfile](../../Dockerfile); [.dockerignore](../../.dockerignore); [server-cost-policy.ts](../../server-cost-policy.ts); [server.ts](../../server.ts#L913-L958)

#### Shape C — Owner's PC + named Cloudflare Tunnel

- This is already documented by the repository as the route with no rented server: run Node, vision, and Ollama on the PC and expose only the Node origin through a managed/named tunnel. The guide explicitly rejects Quick Tunnels for real uptime and notes that the PC, internet connection, backups, electricity, and optional domain remain the operator's responsibility. — [DEPLOY.md](../../DEPLOY.md#L12-L30)
- Required source changes: none. Required operations/config: auto-start all three processes and the tunnel after reboot, use `NODE_ENV=production`, fresh `JWT_SECRET` and `STORAGE_SECRET`, `ENABLE_DEMO_OTP=false`, correct `TRUST_PROXY` and `ALLOWED_ORIGINS`, restrict FastAPI/Ollama to loopback, and back up `data/`, `uploads/`, and `.local-ai`. — [.env.example](../../.env.example#L59-L110); [scripts/start-local-ai.ps1](../../scripts/start-local-ai.ps1)

#### Shapes that do not satisfy “free and available all the time”

- Render free cannot host this full system continuously: free services sleep after 15 idle minutes, a workspace receives 750 free instance-hours total per month (insufficient for two services running continuously), free services have no private-network ingress, and their local filesystem is ephemeral with no free persistent disk. It could host a short-lived demo only after moving persistence and adding an application-level secret to a public vision service. — [Render free services](https://render.com/docs/free); [Render web services](https://render.com/docs/web-services)
- Hugging Face CPU Basic has ample stated CPU/RAM/disk for a vision demo, but free hardware sleeps after inactivity and never-sleep requires paid hardware; current docs also say creating a new compute Space requires a paid plan. Exposing the current unauthenticated FastAPI app as a public Space would violate its intended trust boundary. — [Hugging Face Spaces hardware and sleep](https://huggingface.co/docs/hub/en/spaces-gpus); [fastapi_service/main.py](../../fastapi_service/main.py#L235-L247)
- Pure static hosts (Firebase Hosting, Vercel static, Netlify static) can serve `dist` but cannot replace the resident Node/FastAPI/Ollama processes. Short-lived serverless functions are also mismatched to the local database lock, resident ONNX sessions, background Firestore listener, large request bodies, and multi-minute upstream timeouts described above.

### Inferences
- **Best fit for the literal request:** attempt one OCI Always Free A1 VM, using the single-host topology, because 12 GB RAM and persistent block storage align with the repository's actual loopback, one-writer, and resident-model design. Treat signup/host capacity and lack of SLA as explicit risks; test ARM64 dependency installation and full inference before committing.
- **Best managed low-cost demo:** use the repository's intended Firebase + Cloud Run split with `min-instances=0`, but do not call it “always on.” First fix Node→vision IAM, add the missing Hosting rewrite, migrate all JSON/upload persistence, and decide whether paid Gemini chat is acceptable. Without those fixes it is a test deployment that can lose user/security data.
- **Fewest code changes:** a named tunnel to the existing Windows PC. It preserves local Ollama and disk behavior exactly, but availability is only as good as the PC, ISP, and power; it is not a hosted SLA.
- Avoid changing UI-owned files for infrastructure work. `server.ts`, `server-storage.ts`, FastAPI, `.env.example`, and persistence/auth helpers are backend-owned. Any new npm dependency changes jointly owned `package.json` and must be communicated to Antigravity. `firebase.json`/deployment configuration should be coordinated, while `src/lib/api.ts` needs no change for a same-origin Hosting rewrite or Node-served SPA.
- Preserve the safety boundaries during any migration: do not invent diagnosis fallbacks when vision is cold/down; do not expose FastAPI publicly without authentication; do not silently fall back from durable storage to ephemeral storage in production; and keep paid Gemini/Claude explicitly opt-in.

### Gaps
- OCI's official pages are inconsistent: the current detailed Always Free tenancy documentation says 2 OCPUs/12 GB, while other Oracle marketing/paid-account pages still mention 4 OCPUs/24 GB or 3,000 OCPU-hours/18,000 GB-hours. Capacity and the actual entitlement shown during signup must be checked before planning resources.
- ARM64 compatibility of the exact pinned/transitive versions was not built in this read-only review. Validate `onnxruntime`, Pillow, NumPy, Node 24, `tsx`, and Ollama/Qwen on the selected A1 image.
- Object-storage and full-database adapters do not yet exist. Their exact schema/migration design is a backend decision and should be implemented with tests before public production use.
- No free provider reviewed offers both an uptime SLA and unlimited always-warm compute. “Available by URL after a cold start” and “process stays warm 24/7” must be treated as different requirements.
